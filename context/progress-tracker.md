**Phase:** Phase 20 — In-App Notifications
**Last completed:** Closes the gap between module events and the people who need to act on them — previously blockers, reviews, and milestone risk were all silent. Four notification types: `blocker_assigned` (assigned dev notified when someone else reports a blocker on their module), `sent_to_review` (all leads/PMs notified when a module transitions to review), `dependency_blocked` (assigned devs of downstream modules notified when a dependency goes blocked — deduplicated so one person with multiple dependents gets one notification, not N), `milestone_at_risk` (leads/PMs notified when a milestone transitions to at_risk for the first time). `notifications` table (`userId, organizationId, type, message, resourceId, read, createdAt`) — `resourceId` stores the target URL path (`/projects/{id}/modules/{mid}` or `/projects/{id}`) so the bell can link directly to the affected resource. `milestones.status` column added (`upcoming | at_risk | missed | completed`, default `upcoming`) — written by the new `recalculateMilestoneStatus(projectId, orgId)` helper, which replicates the client-side `getMilestoneStatus` logic server-side and emits the `milestone_at_risk` notification only on transitions (not every recalc). Notification writes are isolated in their own inner try/catch inside each action — a DB error on a notification insert never fails the core operation (blocker creation, progress update). `NotificationBell` client component in Navbar: fetches on mount (badge count), re-fetches on open, 3-row skeleton while the first fetch is in flight (prevents "You're all caught up" flash for users with real notifications), type-colored icons (destructive for blockers, brand for review, warning for dependency/milestone), hover-reveal per-item mark-read and dismiss (both optimistic with revert-on-failure), "Mark all read" button, empty state. `markNotificationRead`/`dismissNotification` return `{ success: boolean }` so the bell can revert optimistic updates on failure. `tsc` clean throughout.

**Post-implementation review fixes:** five issues found by `/review` and resolved — (1) notification writes inside core try/catch (false failure visible to user, blocker created but action returns error) → moved to inner try/catch; (2) `dependency_blocked` duplicate notifications when one developer is assigned to multiple dependent modules → Set-based deduplication during filter; (3) empty state flash on first popover open → 3-row animated skeleton shown while `!hasFetched`; (4) `text-muted-foreground/40` opacity modifier on hex CSS var → replaced with `opacity-40` utility class; (5) `dismissNotification`/`markNotificationRead` returned `void` → now return `{ success: boolean }`, bell component reverts optimistic state on failure.

Fixed by extracting the constant to a new `lib/roles.ts` (no `"use server"` directive) and having both `actions/modules.ts` and `app/my-work/page.tsx` import it from there instead — preserves the single-source-of-truth intent without violating the directive. (One follow-up slip during the fix itself: first attempt added `as const` to the array, which changed its inferred type from `string[]` to a string-literal union and broke the existing `.includes(session.user.role ?? "")` calls — `session.user.role` is plain `string`, not assignable to the narrowed literal type. Caught immediately by `tsc`, reverted to a plain array.) Verified against the actual running dev server post-fix — `/my-work`, `/dashboard`, `/projects` all return `307` (auth redirect, expected for an unauthenticated request) instead of `500`. 103/103 tests still passing, `tsc`/lint clean.

**Last completed:** Closes the gap Phase 14's blocker-type classification deliberately deferred: nothing previously linked one module to another, so a project could show `on_track` even when a downstream module (e.g. Billing) depends on an upstream one (e.g. Authentication) that's silently behind schedule — flat average progress and the single `hasBlockedModule` boolean had no way to see the chain. New pure `lib/dependency-risk.ts`: `computeAtRiskModules(modules, edges, today?)` does a forward BFS from every "broken" module (status `blocked`, or overdue-and-not-`completed`) through the dependency graph, returning the full transitive closure of dependents at risk; `isModuleBroken()` exported separately so display code (badges) doesn't re-derive the same rule. `lib/health.ts`'s `HealthInput` gained `hasDependencyRisk?: boolean` — per explicit user decision, its early-return sits *after* the existing `hasBlockedModule` check and *after* the time-based `high_risk`/`at_risk` checks, so it only ever upgrades `on_track` → `at_risk`, never downgrades a worse verdict. `actions/modules.ts` gained `addDependency`/`removeDependency` (RBAC: `owner`/`team_lead`/`project_manager` only — same set as module creation, no assignee carve-out, per explicit user decision) plus a private `wouldCreateCycle` BFS helper (rejects self-reference, cross-project edges, duplicates, and any cycle — direct or transitive); `recalculateProjectHealth` now fetches the project's edges alongside its modules and feeds `hasDependencyRisk` into the same health calc every other mutation already triggers. New `tests/unit/dependency-risk.test.ts` (14 tests covering direct/transitive/diamond propagation, exclusion of the broken module itself, and the completed-overrides-overdue rule). **Post-implementation review fix** (`/review`): two Important issues, both fixed. (1) `app/projects/page.tsx` (the `/projects` list page) was never updated to account for dependency risk — it recomputes project health live like the dashboard and project detail pages, but its `calculateProjectHealth` call had no `hasDependencyRisk` input, so a project correctly shown "At Risk" everywhere else would still show "On Track" here, with `ProjectsClient.tsx`'s filter-tab counts wrong to match. OAuth sign-in fix — traced through Better Auth's source (`node_modules/better-auth/dist/utils/url.mjs`, `api/routes/sign-in.mjs`) to find that `withPath()` validates `baseURL` via `new URL()` (which silently tolerates `http:host` missing `//`) but then builds the returned string via raw concatenation on the *unnormalized* input, so a malformed `BETTER_AUTH_URL` produces a malformed `redirect_uri` sent to Google/GitHub, which they reject via exact string match (email/password auth unaffected since it doesn't depend on an external redirect_uri).
